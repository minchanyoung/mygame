## 0. Claude Code에 전달할 핵심 지시

이 문서를 프로젝트의 기준 명세로 사용한다. **1차 목표는 완성된 대형 게임이 아니라 처음부터 은퇴까지 진행 가능한 재미있는 수직 슬라이스(MVP)**다. 한 단계씩 구현하고 테스트한 뒤 다음 단계로 넘어간다.

- 먼저 현재 저장소 구조, 기존 코드, 패키지 설정, 테스트 환경을 확인한다. **기존 프로젝트 파일을 임의로 덮어쓰거나 삭제하지 않는다.** 신규 프로젝트인 경우에만 초기화를 제안한다.
- 기술 스택은 아래 권장안을 기본으로 하되 기존 코드가 존재하면 호환성을 우선한다.
- **게임 결과의 권위는 서버**에 둔다. 클라이언트는 서버가 확정한 상태를 표시하고 선택지를 제출한다.
- 게임 로직(시간 진행·확률·효과·조건·경제 계산)과 UI를 분리한다.
- 이벤트·회사·직무·특성 등 콘텐츠는 코드에 하드코딩하지 않고 구조화된 데이터로 관리한다.
- 관리자 페이지는 신규 이벤트를 **코드 수정 없이 등록·수정·검증·게시**할 수 있게 설계한다.
- 모든 랜덤 판정은 재현 가능한 난수 시드를 사용하며 서버에서 기록한다.
- 계획 범위가 커지면 구현 전 작업을 작게 나누고, 각 작업의 **파일 변경 예상 범위·테스트·완료 기준**을 설명한다.
- 외부 서비스 키, 배포 계정, 실명 기업 사용, 결제, 인증 정책처럼 사용자 결정이 필요한 부분은 임의 확정하지 않는다.

### 첫 구현 순서 (상세 작업 분해·검증은 §24 기준)

1. 프로젝트 구조 및 데이터 모델 정리
2. 플레이어 이름·성별 입력 후 해당 프로필을 반영한 랜덤 캐릭터 카드 3장
3. 입사 지원 회사 카드 3장과 채용 판정 + 회사별 랜덤 상사·동료 생성
4. 1개월 진행 엔진 + 이벤트 선택지 + 자원/연봉/생활비 처리 + 특수 사건 성공 시 긍정 영구 능력 획득·강화 및 명시된 특수 사건으로 부정 특성 부여·완화
5. 승진·이직 및 은퇴 조건
6. 은퇴 결과 화면, 세이브/로드
7. 이벤트 관리자 CRUD 및 검증/게시
8. 밸런싱, 모바일 UI, 운영 및 확장 기능

## 1. 게임 개요와 설계 원칙

### 1.1 핵심 콘셉트

플레이어는 **랜덤으로 주어진 출신 배경과 능력**을 지닌 신입 사회인으로 시작한다. 매월 발생하는 회사 생활·경제·인간관계 이벤트에서 선택지를 고르고 커리어, 재산, 건강, 명예, 행복을 관리한다. 승진, 이직, 창업 또는 실패를 거치며 은퇴할 때의 인생을 결정한다.

- 가제: **회사원 키우기** (권장 출시 후보: **월급루프**, 명칭은 출시 전 확정)
- 장르: 선택지형 로그라이크 + 직장/인생 시뮬레이션 + 경량 경제 관리
- 플랫폼: 반응형 모바일 웹(PWA 우선), 데스크톱 웹; 이후 Android/iOS 앱 패키징 검토
- 게임 방식: 싱글 플레이 세션 + 온라인 저장 + 공유 기록/랭킹
- 분위기: 한국 직장생활을 바탕으로 한 블랙코미디, 전략적 선택, 극적인 인생 역전
- 반복 플레이 동기: 랜덤 출신/특성/회사, 이벤트 연쇄, 다양한 성공 기준, 챌린지, 엔딩 수집

### 1.2 게임의 재미를 만드는 핵심 원칙

1. **모든 선택에는 기회비용이 있다.** 고연봉은 스트레스와 시간을 요구하고, 안정성은 낮은 성장률을 동반할 수 있다.
2. **유능함과 출세는 다르다.** 전문성·성과뿐 아니라 인맥·정치력·타이밍이 영향을 준다.
3. **불운은 관리 가능해야 한다.** 플레이어가 위험을 감지하거나 준비할 수 있는 대응책을 제공한다.
4. **과거 선택이 미래를 바꾼다.** 이벤트 플래그와 NPC 기억으로 후속 사건을 발생시킨다.
5. **정답 인생은 없다.** 자산, 직책, 명예, 건강, 행복을 별도로 평가한다.
6. **짧고 명확한 모바일 플레이.** 기본 턴은 1개월, 중요 상황에서만 선택지를 노출한다.

### 1.3 MVP 범위와 명시적 비범위

**MVP에 포함**

- 플레이어가 이름·성별 입력 → **이름·성별은 공통으로 유지**하면서 배경·초기 자원·강점·약점이 서로 다른 랜덤 카드 3장 생성 및 선택
- 대학군, 전공, 출신 배경, 특출난 재능/약점 및 초기 소비 자원 (영구 능력 미보유)
- 조건부 입사 지원 3개(회사 등급, 직무, 합격률, 제시 연봉)
- 채용 성공/실패, 재지원 또는 낮은 등급 회사 대안
- 회사 등급 S/A/B/C/D/F, 직무 5개(개발·인사·영업·재무·기획), 직책 4단계(사원·대리·과장·부장)로 시작
- 월급·세후 수입(간략 모델)·고정 생활비·저축/부채
- 체력·정신력·돈·평판·집중력 등 단기 수치와 **이벤트로만 획득하는 긍정/부정 영구 특성(시작 시 모두 0개)** 분리. MVP 데이터 정의 긍정 6종·부정 6종. **Phase 1 실제 획득/강화/회복 플레이 연결은 긍정 3종·부정 2종**
- 정식 MVP까지 조건부 이벤트 50개 내외(일상/업무/인사/경제/생활)와 일부 연쇄 이벤트. **Phase 1은 15~20개로 제한**
- 선택지 조건, 성공 확률, 즉시 효과, 지연 효과, **이벤트별 능력치 Lv.1/Lv.2 조건과 성공 보정, 특수 이벤트 성공 시 능력 획득·강화**
- 승진, 이직, 해고, 휴직, 은퇴, 파산/건강 위기 처리
- **회사별 랜덤 NPC(상사 1명·동료 2명)와 관계/성격에 따른 이벤트 변형**
- 서버 저장, 이어하기, 은퇴 결과, **개인 완주 기록**(공개 랭킹은 후속 단계)
- **관리자용 최소 이벤트 CRUD + 미리보기/조건 검증/게시(Phase 3);** Phase 1에서는 콘텐츠 JSON 검증 및 서버 로더 우선

**MVP에서 제외하고 확장으로 이관**

- 결혼/자녀/복잡한 가족 관계
- 부동산 매매·대출·투자 시장 정밀 시뮬레이션
- 완전한 창업 경영 게임과 주식회사 회계
- AI가 실시간 생성하는 이벤트 본문
- 실시간 멀티플레이, 유저 간 거래
- 앱스토어 배포 및 유료 결제
- 복잡한 NPC 대화/AI 인격 모델(단, 회사별 **규칙 기반 랜덤 NPC 생성·관계**는 MVP에 포함)

## 2. 핵심 게임 루프

```text
새 게임
  ↓
이름·성별 입력 → 해당 이름·성별이 고정된 랜덤 카드 3장 생성 → 1장 선택
  ↓
출신·특성·직무를 바탕으로 지원 회사 카드 3장 생성
  ↓
1개 회사 지원 → 서버 합격 판정
  ├─ 합격 → 직무·연봉·직책 확정 + 회사 NPC(상사·동료) 생성/연결
  └─ 불합격 → 구직 기간 진행 / 다음 지원 / 구제 옵션
  ↓
[월간 턴 반복]
  1) 전월 지연 효과·상태이상 반영
  2) 급여·부업 등 수입 반영
  3) 월세·생활비·이자 등 지출 처리
  4) 체력·정신력·집중력 등 자연 변화
  5) 조건에 맞는 이벤트 선정 및 선택지 표시
  6) 플레이어 선택 → 서버 조건/레벨별 보너스/NPC 관계/성공 판정 → 효과 적용
     └─ 지정된 특수 사건 성공: 능력 미보유→Lv.1 획득 또는 명시된 강화 조건 충족 시 Lv.2 상승 (XP 없음)
  7) 성과·평판·승진 포인트·이직 가능성 재계산
  8) 상태 및 이벤트 로그 저장
  9) 다음 달 진행 또는 게임 종료
  ↓
승진 / 이직 / 해고 / 휴직 / 창업(후속 버전)
  ↓
은퇴·특별 종료 → 인생 성적표 → 랭킹 → 재도전
```

### 2.1 시간 단위

- 1턴 = 1개월, 기본 시작 24세, 정규 은퇴 60세(모두 설정 가능).
- MVP에서는 매월 **주요 선택 이벤트 1개** + 필요 시 자동 처리되는 부가 결과를 권장한다.
- 연말 평가는 **12월**, 연봉 조정은 **다음 1월**의 예약/정기 이벤트로 수행한다(§20). 채용/이직 시장 및 경제 사건은 조건부 발생.
- 중요 이벤트가 없는 달은 결과 요약 후 다음 달로 빠르게 넘길 수 있다.
- 24~60세 전체 플레이가 길어질 수 있으므로 **연속 진행**, 자동 저장, 선택지 스킵 안전장치를 준비한다.

### 2.2 턴 상태 머신

`CREATED → PROFILE_INPUT → CHARACTER_SELECTION → JOB_OFFERS → JOB_APPLICATION → MONTH_START → EVENT_PENDING → EVENT_RESOLUTION → MONTH_SUMMARY → (MONTH_START | GAME_OVER)`

- 클라이언트 요청으로 임의 상태 단계를 건너뛰지 못하게 한다.
- 이벤트 해결 전에는 다음 달을 진행하지 못한다.
- 동일 선택지 중복 제출은 idempotency key로 한 번만 적용한다.
- 턴 처리 중 예외 발생 시 트랜잭션 롤백으로 일부 자원만 변하는 문제를 방지한다.

## 3. 캐릭터 생성과 직장 선택

### 3.1 플레이어 프로필 입력 → 랜덤 플레이어 카드 3장

**새 게임 시작 시, 카드 생성 전에 플레이어가 이름과 성별을 직접 입력한다.** 이름과 성별은 플레이어가 정한 프로필에 속하며 랜덤 생성 대상이 아니다. 3장의 카드는 **동일한 이름·성별**을 사용하고, 대학·전공·가정환경·재능·약점·초기 자원만 달라진다. 모든 카드의 영구 능력치는 시작 시 비어 있다.

**입력 화면 요구사항**

- `displayName`: 필수, 앞뒤 공백 제거, 2~16자(초기 기준), 허용 문자와 금칙어 정책은 서버에서 검증. 원래 입력한 문자열을 보존하여 UI/엔딩에 표시한다.
- `gender`: 필수 선택값. 예시 `MALE`, `FEMALE`, `OTHER`, `UNSPECIFIED` 중 하나. 서비스 정책에 따라 선택지를 조정할 수 있도록 enum과 표시명을 분리한다. **성별 미공개**도 유효한 선택지로 둔다.
- 플레이어의 이름·성별은 **채용 확률, 초봉, 영구 능력 획득의 우열에 영향을 주지 않는다.** 콘텐츠에서 호칭·대사·일부 배경 표현을 분기할 수 있으나 불이익·고정관념을 주는 필수 규칙으로 사용하지 않는다.
- 클라이언트에서 3장 미리보기 요청을 반복해 유리한 결과를 골라내는 정책은 별도 정한다. MVP 기본값: 새 게임 생성 시 한 번 생성하여 서버에 고정하고 세이브에 저장. 새 게임 재시작 시 새 시드를 사용한다.
- 플레이어 프로필 확정 전에는 카드 생성이 불가능하며, 생성 후 세 카드의 이름·성별이 같아야 한다.

각 카드에는 다음 정보를 보여준다.

| 필드 | 예시 | 용도 |
|---|---|---|
| **플레이어 입력 이름·성별** | 김하늘 / 여성 | 세 카드에 공통 적용, 대사·화면·엔딩 호칭 |
| 시작 나이 | 24세 | 캐릭터 식별·시간 계산 |
| 대학군 | 지방 사립대 | 채용 조건 보정, 일부 이벤트 |
| 전공 | 컴퓨터공학 | 직무 적합도·초기 전문성 |
| 가정 배경 | 학자금 대출 | 시작 자산·부채·생활 이벤트 |
| 강점 | 공감능력 | 인사·갈등 중재·대인관계 보너스 |
| 선천적 약점 | 압박에 약함 | 시작 시 성향/상황 보정. **후천적 부정 특성 `fragileMind`와 별개** |
| **초기 영구 능력치** | 없음 (`{}`) | 모든 캐릭터 공통. 이후 특수 사건으로 획득 |
| 초기 자원 | 체력 70, 정신력 55 | 턴 중 소모 자원 |
| 시작 돈·부채 | 현금 300만원/빚 1,000만원 | 초기 경제 상태 |

**생성 규칙**

- 3장이 완전히 유사하지 않도록, 대학/전공/특성·초기 자원 및 플레이 스타일의 다양성을 보장한다.
- **프로필 정보는 캐릭터 카드 3장 생성 함수의 입력값으로 전달**하고, 카드 생성 RNG는 배경·특성·초기 자원에만 사용한다.
- 희귀 강점에도 단점 또는 기회비용을 주고, 낮은 대학군에도 역전 가능한 장점을 배치한다.
- 특정 학교 출신이라고 반드시 나쁜 엔딩에 도달하지 않도록 확률 보정 상한/하한을 둔다.
- 카드 생성 시 시드와 3장의 실제 결과를 서버 저장하여 리플레이/문제 재현이 가능하게 한다.

**API 흐름(권장)**: `POST /api/runs { displayName, gender }` → 프로필 검증 및 랜덤 카드 3장 고정 → `POST /api/runs/:id/character { cardId }` → 선택 카드 확정. 서버는 임의 인물 데이터가 아니라 미리 발급한 `cardId`만 허용한다.

### 3.2 입사 지원 카드 3장

선택된 캐릭터의 대학군·전공·특성·지원 직무·회사 등급을 반영하여 **서로 다른 위험/보상**을 가진 채용 카드 3개를 제시한다.

예:

| 회사/부서 | 합격률 예시 | 연봉 예시 | 이유 |
|---|---:|---:|---|
| B등급 중견테크 / 개발팀 | 40% | 2,800만원 | 전공 적합도 +, 대학군 보정 - |
| D등급 미래비전 / 인사팀 | 60% | 2,600만원 | 공감능력 강점 + |
| F등급 열정페이 / 개발팀 | 90% | 2,200만원 | 낮은 경쟁률, 취약한 복지 |

수치는 **게임 밸런스 예시**이며 실제 노동시장 통계가 아니다. 지원 실패 시 구직 기간·정신력 비용이 있으나 영구적인 진행 불능은 피한다.

**추천 확률 함수(초안)**

```text
합격확률 = clamp(
  등급별 기본확률
  + 전공 적합도 보정
  + 대학군 보정
  + 강점/약점 보정
  + 경력/평판/전문성 보정,
  0.05, 0.95
)
```

- 보정값과 공식 버전을 설정 데이터에서 관리한다.
- 채용 합격률은 **정확한 %를 공개**한다. 반면 돌발 이벤트는 위험도·특성 보너스 여부만 노출한다(§22).
- 제시 연봉은 `등급 기본값 × 직무계수 × 경력계수 + 특성 보정`으로 계산하며 최소/최대 범위를 설정한다.

### 4.2 영구 능력치 — 사건 기반 획득·강화 시스템 (서울 2033식 감각, MVP 핵심)

> **핵심 변경(v1.2): 영구 능력치의 초기 보유 수는 0개. XP, 경험치 바, 반복 행동 누적 레벨업은 전부 폐지한다.** 특정 **특수 랜덤 인카운터·이벤트의 성공 결과**를 통해 처음 획득하거나 한 단계 강화한다. 이는 사건 기반 특성 시스템의 일반적인 설계 방향을 참고한 것으로, 다른 게임의 고유 텍스트·이벤트·화면을 복제하지 않는다.

- **영구**는 한 번의 인생(run)에서 월간 자원처럼 자동 소모되지 않는다는 뜻이다. 새로운 인생은 다시 `skills = {}`에서 시작한다. 계정 전체 계승은 MVP 범위 밖이다.
- 시작 시 모든 캐릭터 카드의 영구 능력 상태는 **빈 컬렉션**이다. 대학·전공·가정 배경·선천적 강점/약점은 별도 `backgroundTraits`로 관리하고, 영구 능력치로 표시하지 않는다.
- **Lv.0 = 미보유** (UI에는 표시하지 않음); 획득 성공 시 Lv.1. 이후 **희귀 강화 사건**의 조건을 충족하고 성공하면 Lv.2. MVP 상한은 **Lv.2**, 향후 Lv.3 확장 가능하도록 데이터 모델은 상한을 설정화한다.
- **Lv.1이 효과를 주는 이벤트와 Lv.2가 효과를 주는 이벤트는 다르게 설정할 수 있다.** 이벤트별로 필요한 최소 레벨, 레벨별 확률 보너스, 특수 선택지 해금을 명시한다. 전역 'Lv.1 보너스 0' 또는 'Lv.2부터 모든 이벤트 보너스' 규칙은 없다.
- 일반 사건 성공은 재화·평판 등의 일반 보상을 제공할 뿐 **영구 능력치를 무조건 지급하지 않는다.** 오직 명시적으로 `skillGrant`/`skillUpgrade` 결과를 가진 **특수 사건 성공**만 획득·강화를 일으킨다.
- 능력치의 획득·강화는 사건에서 연출되어야 한다. 예: 회식 자리의 갈등을 무마해 **처세술 Lv.1 획득**, 대규모 인사 갈등 중재에 성공해 **처세술 Lv.2 획득**. '같은 행동 10회' 같은 누적 조건은 쓰지 않는다.
- 특수 사건에는 `rarity`, `conditions`, `cooldownMonths`, `maxOccurrencesPerRun`, `outcome.successChance`, `grants` 등을 지정한다. 희귀 특성은 성취감을 주되 필수 진행을 막지 않는다.
- 기본 확률은 `baseChance + eventSkillBonus + npcBonus + negativeTraitBonus + itemBonus + situationalBonus`로 구성하고, 최종 `clamp(0.05, 0.95)` 적용. 보너스 단위는 %p이며 **해당 이벤트에 정의한 보너스만** 사용한다.
- 실패 시 능력 획득·강화는 기본적으로 없음. 일부 사건은 실패로도 새로운 후속 이벤트가 열릴 수 있으나 실패 보상으로 무제한 능력을 지급하지 않는다.
- **긍정적 영구 능력**은 월별 자동 감소하지 않으며 기본적으로 상실되지 않는다. **부정적 영구 특성**은 특정 사건으로만 부여·악화·완화·제거될 수 있으며, 자동 소멸하지 않는다. 해당 조건과 효과를 UI에 설명한다.

#### 초기 구현 추천 능력치 6종

| 능력 | Lv.1 획득 특수 사건(예시) | Lv.1이 효과 있는 이벤트 | Lv.2 강화 특수 사건(예시) | Lv.2가 특히 유리한 이벤트 |
|---|---|---|---|---|
| **처세술** | 상사·동료 사이 오해 중재 성공 | 회식 위기 탈출 `+10%p` | 부서 간 인사 갈등 중재 성공 | 임원 파벌 협상 `+20%p`, 특별 선택지 |
| **업무 감각** | 긴급 업무 실수를 수습 | 단순 프로젝트 일정 조정 `+10%p` | 대형 프로젝트를 단독으로 구제 | 초대형 납기 위기 `+20%p` |
| **협상력** | 첫 거래에서 조건 개선 | 연봉 재협상 `+10%p` | 대형 고객 계약 재협상 성공 | 기업 인수 협상 `+20%p` |
| **위기대응력** | 갑작스러운 사고 대응 성공 | 작은 전산 장애 `+10%p` | 회사 전체 장애 수습 성공 | 재난·대규모 구조조정 `+20%p` |
| **인맥** | 어려운 동료에게 손을 내밀어 관계 구축 | 추천 채용 `+10%p` | 업계 인사들과 장기적인 동맹 구축 | 임원 스카우트 `+20%p` |
| **관찰력** | 회계 문서에서 작은 이상 발견 | 업무 실수 사전 발견 `+10%p` | 내부 부정 정황을 확증 | 고난도 비리 조사 선택지 해금 |

수치는 모두 밸런싱을 위한 예시다. **한 능력이 모든 이벤트에서 증가하지 않는다.** 예를 들어 처세술 Lv.1은 소규모 사내 대인관계 사건에서 +10%p를 주지만 '임원 파벌 협상'은 Lv.2 미만이면 보너스가 없거나 특별 선택지를 제공하지 않는다. 이벤트별로 Lv.1/2 보너스를 각각 `0`으로 설정할 수도 있다.

#### 능력치 효과의 종류 — 확률 보너스 이상으로 확장

1. **성공 확률 보정:** 특정 사건에서 `+10%p` 등.
2. **선택지 해금:** 관찰력 Lv.2가 있어야 '장부의 허점을 지적한다' 선택지 등장.
3. **실패 피해 감소:** 위기대응력 Lv.1이 있으면 실패해도 정신력 손실 -5 완화.
4. **보상 증폭:** 협상력 Lv.2 보유 시 성공 계약의 성과 포인트 추가.
5. **후속 사건 분기:** 인맥 Lv.1이 있으면 헤드헌터 연락 이벤트 풀에 진입.
6. **NPC 시너지/상극:** 처세술 Lv.1 + 권위형 상사에게 보너스, 정직형 상사에게는 효과 없음. 특정 성향별 조건을 명시적으로 구성.

**밸런스 추천:** 단순한 '레벨이 높을수록 항상 상위호환'보다는 **이벤트 조건·직무·NPC 성향별 차별화**를 우선한다. 같은 능력을 Lv.2로 올릴 기회를 잡는 대신 다른 신규 능력을 Lv.1로 획득할 기회를 포기하는 사건도 넣어 빌드 선택의 재미를 만든다. 단, 두 결과를 획득하는 조건은 UI에서 충분히 유추할 수 있게 한다.

#### 처리 예시 A — Lv.1도 유효

```text
'팀 회식 갈등' 기본 성공률 40%
처세술 미보유: +0%p → 40%
처세술 Lv.1: +10%p → 50%
처세술 Lv.2: +12%p → 52%
```

#### 처리 예시 B — Lv.2가 있어야 유효

```text
'임원 파벌 협상' 기본 성공률 25%
처세술 미보유 또는 Lv.1: +0%p → 25%
처세술 Lv.2: +20%p → 45% 및 전용 선택지 활성화
```

#### 처리 예시 C — 특수 사건으로만 획득/강화

```text
게임 시작: skills = {} (영구 능력치 없음)
특수 사건 '위험한 회식 자리' 성공 → grants: 처세술 Lv.1 (새 능력 획득)
이후 특수 사건 '부서 통합 중재' 성공 (처세술 Lv.1 보유 조건)
   → upgrades: 처세술 Lv.2 (레벨 강화)
일반 회식 사건 100번 성공해도 grants/upgrades가 없으면 레벨 변화 없음
```

#### 데이터 저장 예시

```json
{
  "skills": {
    "socialSkill": 2,
    "observation": 1
  },
  "skillHistory": [
    {"eventId": "evt_social_breakthrough", "skillId": "socialSkill", "from": 0, "to": 1, "month": 4},
    {"eventId": "evt_department_mediation", "skillId": "socialSkill", "from": 1, "to": 2, "month": 19},
    {"eventId": "evt_document_clue", "skillId": "observation", "from": 0, "to": 1, "month": 21}
  ]
}
```

- 시작 상태 `skills: {}`; 능력 키 부재 = 미보유 (Lv.0). `0 XP` 필드 자체가 없다.
- 보상 적용은 서버에서 `fromLevel`, `requiredCurrentLevel`, `toLevel`, `maxLevel` 검증 후 **원자적**으로 처리한다.
- 이미 Lv.1인 능력을 다시 획득하는 경우 자동 Lv.2 강화하지 않는다. `grant`는 미보유 상태만, `upgrade`는 명시한 현재 레벨에만 사용한다. 중복 획득 시에는 별도 대체 보상(작은 평판 등)을 정의하거나 발생 대상에서 제외한다.
- 선택지 성공 판정에는 **사건 해결 직전의 능력 레벨**을 사용하고, 획득/강화 효과는 결과 판정이 끝난 뒤 적용한다.
- 영구 능력 UI는 획득한 능력만 보여주며, 미보유 영역은 '발견한 특성 0개' 정도로 표시한다. 획득 순간에는 이름·레벨·효과와 획득 경위를 연출한다.

### 4.2.1 특수 사건 설계와 드롭 제어

- 희귀 특성 획득 이벤트는 특정 직무/NPC/회사 등급만 요구하지 않도록 다양한 루트로 제공한다.
- 특수 이벤트 후보가 전체 이벤트를 잠식하지 않도록 별도 `specialWeight` 또는 이벤트 풀을 두되, **희귀가 곧 확률상 불가능에 가깝지는 않게** 시뮬레이션으로 검증한다.
- '보유한 특성이 새로운 획득 사건을 열어주는 체인'은 허용하되, 2~3개의 핵심 기초 능력 획득 기회는 모든 진로에서 제공한다.
- 한 번 선택한 특수 이벤트가 실패하면 결과가 기록되며, 정해진 조건에서 다른 획득 루트가 열릴 수 있게 한다. 특정 단일 사건에 영원히 의존하지 않는다.
- 능력 획득/강화 이벤트는 사전에 스포일러하지 않으면서, 플레이어가 선택의 중요성을 이해할 정도의 대사 힌트를 제공한다.

### 4.2.2 부정적 영구 특성 — MVP 6종 (v1.3 추가)

**설계 원칙**

- 신규 run에서 `skills = {}`와 `negativeTraits = {}` 둘 다 빈 상태다. 캐릭터 카드의 **선천적 특성**(`backgroundTraits`, 출생/학력/기질 등 시작 배경)과 사건으로 획득하는 **후천적 특성**(`skills`, `negativeTraits`)은 별개다. 선천적 약점 이름이 후천적 특성과 동일하지 않도록 콘텐츠 명칭을 구분한다.
- 경험치/XP는 사용하지 않는다. `negativeTraits[traitId] = 1 | 2`만 저장하고, 키가 없으면 미보유다.
- 긍정 영구 능력과 달리 부정 특성은 **특수 사건 실패**, **위험한 선택의 확정 결과**, 또는 **관련 사건의 분기**에서 얻을 수 있다. 통상적인 실패마다 자동 부여하지 않는다.
- Lv.1에서 Lv.2로의 악화는 명시된 특수 사건으로만 발생하며, 단순히 3개월이 지났다는 이유로 악화되지 않는다.
- 완화(`Lv.2 → Lv.1`)와 극복(`Lv.1 → 미보유`) 역시 특정 사건과 조건을 통해 처리한다. 필요에 따라 Lv.2에서 바로 제거하는 희귀 사건도 정의할 수 있다.
- 부정적 특성으로 플레이가 막히지 않도록 모든 특성은 최소 2가지의 극복 루트(예: 휴직/멘토 이벤트)를 고려한다. 회복 방법은 직무나 특정 NPC에 종속되지 않게 한다.
- 이벤트의 효과는 전역 페널티가 아니라 조건별로 부여한다. 예: `유리멘탈 Lv.1`은 갈등 사건의 정신력 피해를 증가시키지만 모든 선택의 성공률을 낮추지는 않는다.
- 하나의 사건에서 `성공률 보너스/페널티`를 합산한 뒤 5~95% 범위를 적용한다. `피해 보정`은 성공률 계산과 분리한다.
- 부정적 특성의 사건은 비하나 낙인이 아닌 게임 내 상태로 표현한다. 건강 관련 표현은 실제 의학적 진단으로 혼동되지 않도록 서술한다.

| 특성 | 특별 획득 사건(예시) | Lv.1 효과 예시 | Lv.2 효과 예시 | 완화/제거 사건(예시) |
|---|---|---|---|---|
| **번아웃** (`burnout`) | 고강도 프로젝트 후 복구 실패 | 휴식 사건 체력 회복량 `-5` | 업무 압박 이벤트 성공률 `-10%p` | 유급 휴직을 활용한 재정비 성공 → 2→1; 생활 리듬 회복 성공 → 1→0 |
| **유리멘탈** (`fragileMind`) | 공개 질책 후 대응 실패 | 대인 갈등 사건 정신력 피해 `+5` | 고압 협상 성공률 `-15%p` | 멘토와의 대화 성공 → 2→1; 갈등 중재 성공 → 1→0 |
| **사내 낙인** (`officeStigma`) | 공로 가로채기·누명 사건 해결 실패 | 현재 회사 내 평판 이벤트 `-10%p` | 현재 회사 승진 심사 보정 `-15%p` | 진상 규명 성공 → 2→1; 공식 명예 회복 → 1→0 |
| **워커홀릭** (`workaholic`) | 무리한 추가 근무를 자발적으로 수락 | 휴식 선택 시 정신력 회복 `-5` | 회복량 감소 추가, 대신 특정 야근 업무 `+5%p` | 일과 삶의 경계 세우기 사건 성공 → 2→1 → 0 |
| **소비 중독** (`impulseSpending`) | 고위험 소비 유혹 선택 실패 | 소비 이벤트 지출 `+10%` (원 단위 정수 반올림) | 고액 소비 유혹 사건 가중치 증가 | 예산 계획 수립 성공 → 2→1; 충동구매 거절 성공 → 1→0 |
| **불신** (`distrust`) | 믿었던 동료에게 배신당함 | 동료 협업 사건 성공률 `-10%p` | 신규 NPC 신뢰 형성 사건 성공률 `-15%p` | 신뢰를 회복한 협업 성공 → 2→1; 새 동료와 동맹 형성 → 1→0 |

모든 수치는 **기획 초기 임시값**이고 이벤트마다 적용 여부를 명시한다. `사내 낙인`은 현재 회사와 연동할지, 산업 전체 평판까지 이어질지를 데이터로 설정한다. 이직 시 무조건 해제되지 않으며 명시된 해제 조건이 있어야 한다.

**이전 서버 이벤트 효과 예시 (개념 설명용; 구현 시 §23.2 표준으로 변환):**

```json
{
  "id": "evt_public_blame",
  "special": true,
  "choices": [
    {
      "id": "confront",
      "outcome": { "baseChance": 0.4 },
      "onFailure": {
        "negativeTraitGrant": {
          "traitId": "officeStigma",
          "requiredCurrentLevel": 0,
          "toLevel": 1
        }
      }
    }
  ]
}
```

**이전 회복 사건 예시 (개념 설명용; 구현 시 §23.2 표준으로 변환):**

```json
{
  "id": "evt_clear_reputation",
  "special": true,
  "conditions": { "negativeTraits": { "officeStigma": { "minLevel": 1 } } },
  "choices": [
    {
      "id": "present_evidence",
      "outcome": { "baseChance": 0.55 },
      "onSuccess": {
        "negativeTraitRecover": {
          "traitId": "officeStigma",
          "fromLevel": 1,
          "toLevel": 0
        }
      }
    }
  ]
}
```

**상태 예시:**

```json
{
  "skills": {},
  "negativeTraits": { "burnout": 1, "distrust": 2 },
  "traitHistory": [
    {"eventId": "evt_project_collapse", "traitId": "burnout", "from": 0, "to": 1, "reason": "grant"},
    {"eventId": "evt_colleague_betrayal", "traitId": "distrust", "from": 0, "to": 1, "reason": "grant"},
    {"eventId": "evt_double_betrayal", "traitId": "distrust", "from": 1, "to": 2, "reason": "worsen"}
  ]
}
```

**중복·충돌 방지:** 미보유에만 `grant`, Lv.1에만 `worsen(1→2)`, 현재 레벨 일치 시에만 `recover` 적용. 한 이벤트의 보상은 서버 트랜잭션에서 원자적으로 기록하고 재시도해도 중복 지급되지 않게 한다. 긍정적 `위기대응력`과 부정적 `번아웃` 같은 상반된 특성이 공존할 수 있고, 각 이벤트에서 명시된 효과만 결합한다.

### 4.3 숨겨진 상태

상사 호감도, 상사 신뢰도, 사내 적대 관계, 회사 재정 상태, 구조조정 위험, 누적 번아웃, 내부고발 플래그 등. MVP에서는 복잡도를 낮추기 위해 숨겨진 상태 3~5개만 도입한다.

### 4.4 수치 처리 규칙

- 정수 능력치에는 공통 `clamp(0,100)` 적용.
- 화폐는 **원화 정수**(KRW)로 저장한다. 부동소수점으로 금액을 계산하지 않는다.
- 자산은 `현금 + 투자/부동산 평가액 - 대출잔액`으로 계산하되 MVP에서는 현금/부채만 반영해도 된다.
- 누적 근로소득, 누적 소비, 최고 직책, 이직 횟수는 별도 통계로 저장한다.
- 이벤트 효과는 `즉시`, `다음 달`, `N개월 후`, `매월 반복` 네 종류를 지원할 수 있는 구조로 설계하되 MVP는 즉시/다음 달부터 구현한다.

## 5. 회사·직무·직책

### 5.1 회사 등급

| 등급 | 특징 | 이벤트 방향 |
|---|---|---|
| S | 고연봉, 최고 명성, 성과 압박 | 대규모 프로젝트·임원 정치·주가 충격 |
| A | 높은 복지, 경쟁, 전문 업무 | 조직개편·기술 변화·승진 경쟁 |
| B | 중견 안정성, 성장 기회 | 납기·거래처·인력난 |
| C | 평균적 연봉·복지 | 일상 업무·부서 갈등 |
| D | 약한 복지·불안정한 성장 | 책임 전가·갑작스러운 업무 |
| F | 임금 체불·과도한 업무 위험 | 하청·사장 지시·폐업 위험 |

- 각 회사에 `grade`, `industry`, `cultureTags`, `salaryBand`, `workload`, `stability`, `growth`, `promotionPolicy`, `financialHealth`를 부여한다.
- 회사의 등급은 장기적으로 변화 가능하도록 데이터 모델을 구성한다. MVP는 드문 변화 이벤트만 제공한다.
- 회사 이름은 **가상의 패러디 명칭**을 우선 사용한다. 실존 기업 이름·로고·상표의 사용은 별도 검토 없이 확정하지 않는다.

### 5.2 직무

초기: 개발(전문성/집중력), 인사(공감/처세), 영업(협상/인맥), 재무(재테크/분석), 기획(창의/정치). 확장: 법무, 생산관리, 마케팅, AI연구, 비서실 등.

### 5.3 직책

초기: `STAFF(사원) → ASSISTANT_MANAGER(대리) → MANAGER(과장) → DEPARTMENT_HEAD(부장)`

추후 인턴, 차장, 임원, 대표를 추가한다. 직책에 따라 **동일 사건의 책임 범위와 선택지**를 달리한다.

### 5.4 승진과 이직

승진 판정은 `성과 + 승진 포인트 + 직무 전문성 + 상사 평가 + 정치력 + 공석 여부`로 구성한다. 경험치만 쌓으면 자동 승진하는 방식은 피한다.

이직은 조건 만족 시 지원 회사 3장 생성 → 합격 판정 → 급여/직무/직책 변경 → 기존 관계 일부 단절 및 새 회사 관계 생성으로 처리한다.

## 6. 월간 경제·생활 시스템

### 6.1 월간 정산

1. 고용 상태 확인(재직/실업/휴직)
2. 월 세후 수입 반영 — MVP는 **간략화된 게임 세율** 적용, 실제 세법 시뮬레이션 아님
3. 주거비·식비·교통비 등 월 고정비 지출
4. 부채 이자 및 상환 처리
5. 이벤트 수입/지출 적용
6. 월간 재정 요약 및 잔액 갱신

### 6.2 생활 아이템

- **주거**: 부모님 집, 고시원, 원룸, 오피스텔, 아파트 등. 입주 비용·월 비용·회복량/명성 차등.
- **차량**: 경차~고급차. 구입비/유지비/명성 및 직무별 효과.
- **아이템**: 정장, 노트북, 자격증, 헬스장 회원권 등. 능력치 직접 상승보다 **이벤트 조건·선택지 해금** 위주로 설계한다.
- MVP는 주거 3종과 소비 아이템 5종부터 시작한다.

### 6.3 시간 자원(2차 도입 권장)

월간 자유시간 포인트를 자기계발·운동·휴식·부업에 배분하게 하면 커리어 성장과 생활의 상충 관계를 표현할 수 있다. MVP에서는 UI 복잡성을 고려해 우선 보류한다.

## 7. 이벤트 엔진 — 가장 우선시할 핵심 시스템

### 7.1 이벤트 분류

- 일상: 지각, 회식, 상사 심부름
- 직무: 서버 장애, 채용 면접, 계약 협상, 회계 감사
- 회사: 구조조정, 부서 이동, 프로젝트 실패, 승진 경쟁
- 관계: 동료 갈등, 상사 신뢰, 과거 인연
- 경제/사회: 불황, 기술 혁신, 급격한 시장 변화
- 생활/위기: 질병, 이사, 해고, 금융 위기
- 희귀: 창업 제안, 특별 스카우트, 인생 역전

### 7.2 이벤트 구성 필드

```text
id, version, status(draft/published/archived)
title, description, category, tags, rarity, weight
conditions: 최소/최대 나이, 회사 등급, 직무, 직책,
            능력치 범위, 아이템, 플래그, 고용 상태
cooldownMonths, maxOccurrencesPerRun, exclusiveGroup
choices[]:
  id, label, visibleIf, enabledIf, requirementHint
  outcome: 판정 공식, 기본 성공 확률, 능력 레벨별 보너스, NPC 보정
  onSuccess.grants / onSuccess.upgrades: 특수 사건 성공 시에만 긍정 영구 능력 획득/강화 (XP 없음)
  onFailure.negativeTraitGrant / onChoice.negativeTraitGrant: 특수 사건에서 부정 특성 부여
  negativeTraitWorsen / negativeTraitRecover: 명시적 악화/완화/제거 (XP 없음)
  onSuccess / onFailure / guaranteedEffects
  followUp: 지연 개월, 이벤트 id, 생성 플래그
```

### 7.3 추첨 로직

1. 현재 진행 상태에서 발생 가능한 이벤트를 필터링한다.
2. 쿨다운·중복 금지·독점 그룹·연쇄 이벤트 우선순위를 적용한다.
3. 강제 이벤트(예: 예정된 후속 사건)가 있으면 먼저 처리한다.
4. 남은 이벤트는 `weight / 전체 weight 합` 방식으로 추첨한다.
5. 미리 계산된 시드 기반 RNG에서 결과를 판정하고 로그에 저장한다.
6. 하나의 이벤트가 반복적으로 발생하지 않게 최근 발생 페널티를 적용한다.
7. 이벤트 후보가 0개면 안전한 범용 이벤트 또는 `평온한 한 달`을 제공한다.

**주의:** 이벤트 가중치 `15`는 발생 확률 `15%`가 아니다. 성공 확률과 이벤트 추첨 가중치는 다른 값이다.

### 7.4 예시 연쇄 이벤트

`상사의 비리 발견` →
- 무시: 6개월 뒤 회사 감사 이벤트에서 역풍 가능
- 신고: 내부고발자 플래그 획득 → 신뢰/보복/법적 대응 이벤트
- 협상: 단기 승진 보너스 가능 → 추후 폭로 위험

과거 선택을 기록하는 `flags`와 `scheduledEvents`를 사용한다.

### 7.5 예시 JSON (v1.3 이해용 예시; 구현 스키마는 §23.2 우선)

```json
{
  "id": "evt_office_dinner_crisis",
  "version": 1,
  "status": "published",
  "title": "회식 자리의 불화",
  "category": "social",
  "rarity": "common",
  "weight": 20,
  "conditions": {"employment": "employed"},
  "choices": [
    {
      "id": "mediate",
      "label": "분위기를 수습한다",
      "outcome": {
        "baseChance": 0.4,
        "skillModifiers": [
          {"skillId": "socialSkill", "minLevel": 1, "bonus": 0.10},
          {"skillId": "socialSkill", "minLevel": 2, "bonus": 0.12}
        ],
        "modifierStacking": "highest_per_skill"
      },
      "onSuccess": {"stats": {"reputation": 5}},
      "onFailure": {"stats": {"mental": -5}}
    }
  ]
}
```

위 예시의 `minLevel` 보정은 **동시에 누적하지 않는다**. 보유 레벨을 충족하는 가장 높은 임계값 1개만 적용한다(Lv.2라면 +12%p, +22%p가 아님).

**특수 획득 이벤트 예시:**

```json
{
  "id": "evt_social_breakthrough",
  "rarity": "rare",
  "conditions": {"skillAbsent": ["socialSkill"]},
  "choices": [
    {
      "id": "resolve_conflict",
      "label": "갈등을 직접 해결한다",
      "outcome": {"baseChance": 0.35},
      "onSuccess": {
        "grants": [{"skillId": "socialSkill", "requiredCurrentLevel": 0, "toLevel": 1}]
      }
    }
  ]
}
```

**강화 이벤트 예시:** `conditions.skillLevels.socialSkill = {min:1,max:1}`을 요구하고 성공 결과에 `"upgrades":[{"skillId":"socialSkill","requiredCurrentLevel":1,"toLevel":2}]`를 둔다.

- 모든 이벤트 JSON은 서버에서 Zod 등으로 검증하고 조건은 선언형으로만 처리한다. `eval` 금지.
- 이벤트 관리자에서 `skillAbsent`, `skillLevels`, `skillModifiers`, 특수 획득/강화 결과, 중복 지급 보호, NPC 관계 조건을 편집/미리보기한다.
- 서버에서 능력치 변경은 명시된 이벤트 성공 결과로만 허용한다. 일반 이벤트의 능력 획득·강화 관련 속성은 사용하지 않는다.
- 이벤트 수정으로 기존 세이브가 깨지지 않도록 이벤트 버전과 run 콘텐츠 버전을 기록한다.

## 8. 회사별 랜덤 NPC 및 관계 시스템 (MVP 핵심)

**매 플레이마다 회사에 입사할 때 상사·동료 NPC를 랜덤으로 생성**한다. 같은 회사에 입사하더라도 좋은 상사/동료를 만날 수도, 불합리한 상사/경쟁적인 동료를 만날 수도 있어야 한다. 단순 외형 랜덤이 아니라 **성격·업무 성향·호감/신뢰·보유 특성**이 실제 이벤트 발생과 결과에 영향을 주어야 한다.

### 8.1 생성 시점 및 인원

- MVP: **회사 입사 시 직속 상사 1명 + 동료 2명**을 생성하거나, 이미 그 플레이에서 해당 회사에 생성된 팀이 있다면 재사용한다. 추후 팀원·후배·임원 확장.
- 한 번 생성된 NPC의 **성격과 고유 ID는 해당 run에서 안정적으로 유지**한다. 월마다 NPC를 다시 생성하면 안 된다.
- 이직하면 새로운 회사의 상사/동료를 생성하고, 이전 회사 NPC는 관계/이력 데이터에 보존한다. 동일 회사 재입사 시 재사용하거나 조직개편 이벤트로 교체하는 정책은 명시적으로 적용한다.
- 플레이어가 같은 회사의 다른 부서로 이동하면 팀별 NPC 구성을 별도로 관리한다.
- **회사 성격(`cultureTags`)에 따른 생성 가중치**는 적용할 수 있지만 같은 등급/회사에서도 긍정·부정 성향 NPC가 모두 발생할 수 있어야 한다. 특정 회사가 좋은 상사만 나오거나 나쁜 상사만 나오지 않도록 한다.

### 8.2 NPC 데이터 구성

| 필드 | 내용 |
|---|---|
| `npcId`, `runId`, `companyId`, `teamId` | NPC 고유 ID/소속 |
| `name`, `role`, `rank` | 랜덤 이름, 상사/동료, 직책 |
| `personalityTags` | 배려형, 완벽주의, 권위적, 책임전가형, 협력적, 경쟁적 등 |
| `competence`, `fairness`, `ambition` | 업무 능력, 공정성, 야망(0~100) |
| `favor`, `trust`, `rivalry` | 플레이어에 대한 호감, 신뢰, 경쟁심(0~100) |
| `memoryFlags`, `relationshipHistory` | 이벤트 선택/도움/배신 등 주요 기억 |
| `active`, `createdAtTurn` | 퇴사/부서 이동/생성 시점 관리 |

**성향 예시(초기 풀)**

- 좋은 상사: `MENTOR`(멘토형, 업무 전문성 성장 이벤트 증가), `FAIR`(공정형, 평가 부당 페널티 감소), `SUPPORTIVE`(지원형, 업무 위기 시 도움).
- 나쁜 상사: `AUTHORITARIAN`(권위적, 스트레스 이벤트 증가), `CREDIT_STEALER`(공 가로채기), `BLAME_SHIFTER`(책임 전가).
- 좋은 동료: `HELPFUL`(협력형, 프로젝트 보정), `LOYAL`(의리형, 관계 연쇄 이벤트), `SKILLED`(유능한 동료, 학습 기회).
- 나쁜 동료: `COMPETITIVE`(승진 경쟁), `GOSSIPER`(소문 확산), `FREE_RIDER`(무임승차).
- 태그가 **선악을 완전히 결정하지 않도록** 혼합 성향·능력치·관계 변화를 허용한다. 예: 권위적인 상사이지만 능력은 뛰어나고 높은 신뢰를 보일 수 있음.

### 8.3 NPC가 게임에 미치는 영향

1. **이벤트 후보 가중치**: 권위적 상사가 있으면 야근/질책 이벤트 가중치 상승, 멘토형이면 교육/기회 이벤트 상승.
2. **선택지 해금**: 신뢰도 70 이상 동료의 도움 요청, 경쟁심 80 이상 동료의 견제 이벤트.
3. **성공률 수정**: 협력 동료 +5%p, 방해 동료 -5%p 등. 단, NPC가 실제 사건에 참여하는 경우에만 적용하고 로그에 사유 기록.
4. **후속 기억**: 과거 도와준 동료가 수년 뒤 타사 채용 추천, 공을 가로챈 상사와의 재회 등.
5. **NPC 교체/관계 변화**: 승진/퇴사/조직개편 이벤트로 NPC 역할이 바뀌어도 과거 관계 이력 유지. **플레이어가 상사의 직급 이상으로 승진하면 현재 직속 상사 역할을 해제하고 더 높은 직급의 NPC를 재배치/생성하며, 기존 NPC의 ID·기억은 보존한다(§21).**

**서버 재현성**: NPC 생성은 **회사+팀+run+입사 시점에 결합된 시드 기반 RNG**로 수행한다. 데이터 저장 후 재접속/새로고침 시 다시 굴리지 않는다. 생성 결과는 서버에서 확정한다.

### 8.4 랜덤 생성 예시

```json
{
  "npcId": "npc_run01_teamDev_boss01",
  "companyId": "company_mirae",
  "teamId": "DEV",
  "role": "BOSS",
  "name": "박지훈",
  "rank": "MANAGER",
  "personalityTags": ["AUTHORITARIAN", "SKILLED"],
  "competence": 88,
  "fairness": 24,
  "ambition": 76,
  "favor": 40,
  "trust": 50,
  "rivalry": 15,
  "memoryFlags": []
}
```

### 8.5 NPC 이벤트 예시

- 좋은 상사: **"팀장이 직접 코드를 리뷰해줬다"** → 지정된 희귀 멘토링 사건 성공 시 **업무 감각 Lv.1 획득** (이미 보유하면 중복 보상 없음).
- 나쁜 상사: **"팀장이 성과를 가로챘다"** → 처세술 Lv.2 이상 전용 반박 선택지 또는 기본 선택지 성공률 보너스.
- 좋은 동료: **"동료가 실수의 원인을 함께 찾아줬다"** → `crisis` 이벤트 성공률 +5%p.
- 나쁜 동료: **"동료가 회의에서 책임을 떠넘겼다"** → 신뢰/정치/위기대응력 기반 선택지.

### 8.6 MVP 범위 구분

MVP에 포함: 입사별 랜덤 NPC 3명, 8~12종 기본 성향, 관계 3개, NPC 태그 연동 이벤트 6~10개, 상사/동료 목록 화면, 저장/재접속 안정성.

후속 확장: NPC 간 관계 그래프, 실시간 대화, 가족/연애, 퇴사 뒤 업계 네트워크, 사내 조직도 시각화.

## 9. 종료 조건과 평가·랭킹

### 9.1 종료 조건

- 기본: 정해진 은퇴 연령 도달
- 특수: 조기 은퇴(충분한 자산), 장기 실업/파산, 건강 위기로 인한 조기 종료 등
- `체력=0`, `정신력=0`이 곧 즉사/즉시 종료되는 설계는 지양한다. 병가·휴직·치료·회복 선택지로 완충한다.

### 9.2 인생 성적표

- 은퇴 시점 순자산, 최고 직책, 평생 누적 근로소득, 이직 수, 근무 연수
- 최종 건강·정신력, 관계 점수, 명성
- 주요 전환점 5~10개로 구성된 **인생 연대기**
- 돈/권력/행복 등 별도 세부 등급과 종합 엔딩 칭호

### 9.3 랭킹

- 최종 순자산, 누적 소득, 최고 직책, 명성, 행복, 초기 조건 대비 성장률
- 초기에는 싱글플레이 기록 화면부터 구현하고 온라인 랭킹은 인증·부정행위 검증과 함께 추가한다.
- 온라인 랭킹은 난수 시드/세션 이벤트 로그 및 서버 확정 결과만 집계한다.
- 플레이어 닉네임은 금칙어/길이 제한 등을 적용하고 공개 범위를 설정한다.

## 10. 화면 및 UX 설계

### 10.1 플레이어 화면

1. **시작 화면** — 새 게임/이어하기/랭킹/설정
2. **이름·성별 입력** — 플레이어 프로필 작성·검증
3. **캐릭터 선택** — 동일한 이름/성별의 3장 비교, 상세 출신·강점·약점 (영구 능력치는 모두 미보유), 선택 확정
4. **회사 지원** — 3개 회사의 **정확한 합격률**/연봉/직무/위험도 비교
5. **메인 대시보드** — 나이·연월, 회사/직책, 체력·정신력·돈·평판, 다음 달
6. **이벤트 화면** — 상황 설명, 선택지 2~4개, 조건/위험 힌트. **일반 돌발 사건의 정확한 확률은 숨기고 위험도(낮음/보통/높음) 및 적용 중인 특성 보너스만 공개**
7. **선택 결과** — 성공/실패, 자원 증감, 새 플래그, 후속 사건 암시
8. **월간 결산** — 급여/생활비/변동, 승진 포인트 변화
9. **커리어** — 이력, 승진, 이직 공고, 재직 상태
10. **자산/생활** — 주거·아이템·고정비
11. **동료·상사/성장 능력** — 회사 NPC 관계, 획득한 영구 능력 Lv.1/2·사건별 효과 표시
12. **은퇴 성적표** — 종합 엔딩, 연대기, 랭킹, 공유 카드

### 10.2 모바일 디자인 원칙

- 세로 화면 우선; 중요한 정보는 스크롤 상단에, 행동 버튼은 하단에 배치한다.
- 선택지는 큰 터치 타깃(가능하면 최소 약 44px 높이), 분명한 상태 표시.
- 긴 수치 설명 대신 요약 표시 + 상세 정보 펼치기 제공.
- 색상만으로 성공/실패를 구별하지 않고 텍스트/아이콘도 함께 제공한다.
- `prefers-reduced-motion`, 읽기 쉬운 타이포그래피, 명확한 대비를 고려한다.
- 이벤트 일러스트는 필수가 아니다. MVP는 카드 UI·아이콘·색상만으로 완성 가능하게 한다.

## 11. 기술 아키텍처 권장안

> 아래 기술은 **확정 요구사항이 아닌 권장 기본안**이다. Claude Code는 실제 프로젝트의 버전과 기존 구조를 먼저 확인한 후 채택한다.

| 영역 | 권장 기술 | 이유 |
|---|---|---|
| 웹 UI | React + TypeScript + Vite | 반응형 SPA, 생산성 |
| 스타일 | Tailwind CSS 또는 CSS Modules | 모바일 카드 UI 구현 |
| 라우팅 | React Router | 화면 전환 |
| 데이터 요청 | TanStack Query | 서버 상태 관리 |
| API/게임 서버 | Node.js + TypeScript (Fastify 또는 Express) | 단일 언어, 검증·테스트 용이 |
| 데이터베이스 | PostgreSQL | 세션·콘텐츠·랭킹의 관계 데이터 |
| DB 접근 | Prisma 또는 Drizzle | 타입 기반 쿼리/마이그레이션 |
| 데이터 검증 | Zod | 관리자 입력·API 페이로드 검증 |
| 테스트 | Vitest + Playwright | 게임 규칙/브라우저 E2E |
| 인증 | 간편 계정/게스트 세션으로 시작 | 진입 장벽 축소 |
| 모바일 앱 | PWA 우선, 이후 Capacitor 검토 | 웹 코드 재사용 |

### 11.2 게임 엔진의 책임

다음 함수는 가급적 입력 상태를 받아 새 결과를 돌려주는 **순수 함수**로 구현한다.

- `generateCharacterCards(profile, seed)`
- `generateJobOffers(character, economy, seed)`
- `calculateHireChance(character, offer)`
- `resolveJobApplication(state, offerId, rng)`
- `generateCompanyNpcs(runId, companyId, teamId, rng)`
- `getNpcEventModifiers(state, event, choice)`
- `getEventSkillModifier(skillId, currentLevel, eventChoice)`
- `grantSkillFromEvent(state, eventId, skillId)` / `upgradeSkillFromEvent(state, eventId, skillId)`
- `getEligibleEvents(state, content)`
- `selectEvent(events, rng)`
- `getAvailableChoices(state, event)`
- `resolveChoice(state, eventId, choiceId, rng)`
- `applyMonthlySettlement(state, rules)`
- `evaluatePromotion(state, rules)`
- `evaluateGameOver(state, rules)`
- `calculateLifeScore(state)`

`rng`는 의존성 주입으로 전달하여 동일 상태/시드에서 동일 결과를 재현한다.

### 11.3 데이터베이스 주요 테이블/컬렉션

- `users`: 회원/게스트 식별
- `game_runs`: 1회 플레이 세션, 시드, 엔진/콘텐츠 버전, 현재 단계, 종료 여부
- `characters`: 플레이어 입력 프로필(이름·성별) 및 선택 카드 출신·특성·나이·단기 자원
- `character_cards`: 새 게임 생성 시 고정된 3개 후보 카드(또는 `game_runs`의 버전 관리 JSON)
- `character_skills`: run별 **획득한 긍정 영구 능력 키·레벨만** 저장 (미보유 행 없음). `skill_history`: 획득/강화 사건·전후 레벨·월 기록
- `character_negative_traits`: run별 획득한 부정 특성 키·레벨만 저장. `negative_trait_history`: 획득·악화·완화·제거 사건/전후 레벨 기록. 기존 유저 데이터가 있으면 마이그레이션 설계
- `companies`: 회사 메타데이터, 등급, 문화, 재정 상태
- `jobs`: 직무·직책·연봉 조건
- `employments`: 입퇴사·승진 이력
- `inventories`: 주거/차량/아이템 소지
- `run_npcs`: 회사·팀별 생성된 NPC의 고유 ID·이름·역할·성향·기본 능력
- `npc_relations`: NPC 관계 수치 및 플래그
- `event_definitions`: 이벤트 본문, 조건, 선택지, 버전, 게시 상태
- `event_occurrences`: 발생 이벤트, 추첨/선택 결과, 턴, 중복 방지 키
- `scheduled_events`: 지연/연쇄 이벤트
- `run_snapshots`: 턴별 또는 주기별 저장 상태
- `rankings`: 검증된 완주 기록
- `admin_audit_logs`: 이벤트 등록·수정·게시 이력

상태는 `game_runs`의 버전/스냅샷과 로그를 조합해 저장하되, **DB 정규화와 처리 속도 사이에서 MVP 수준에 맞는 구조**를 선택한다. 무조건 모든 값을 각각의 테이블로 분리할 필요는 없다.

### 11.4 API 엔드포인트(초안)

```text

GET    /api/runs/:id/current-event   현재 이벤트 조회
POST   /api/runs/:id/choose          선택지 결과 확정
GET    /api/runs/:id/npcs            현재 회사의 상사·동료 및 관계
GET    /api/runs/:id/skills          획득한 긍정 영구 능력 레벨·사건별 효과·획득 이력
```

## 12. 관리자 페이지 설계

### MVP 필수 기능

- 이벤트 목록: 상태(초안/게시/보관), 검색, 필터(등급·직무·직책·태그)
- 이벤트 편집: 제목/본문/발생 조건/가중치/쿨다운/선택지/효과/후속 이벤트

- 부정 특성 이벤트 편집: `grant/worsen/recover`, Lv.1/2별 페널티, 회복 조건, 이벤트 전용 적용 범위, 미보유/최대 레벨 분기 검증

- 안전한 스키마 검증: 존재하지 않는 능력치·회사 등급·이벤트 참조 검출
- 미리보기: 선택지 노출, 조건 충족 여부, 레벨/NPC별 성공 확률 및 성공 시 획득/강화할 능력
- 테스트 실행: 샘플 캐릭터 상태로 선택 결과 시뮬레이션
- 게시/보관/버전 관리: 초안 수정이 실시간 진행 중 콘텐츠에 바로 반영되지 않도록 분리
- 관리자 인증 및 변경 이력

### 2차 추가

- 후속 이벤트 그래프 보기

## 13. 밸런스 설계

### 13.1 가설적 초기 수치

- 시작 나이: 24세; 정규 은퇴: 60세
- 게임 턴: 1개월
- 주요 이벤트 빈도: 기본 월 1회
- 성장 능력: **처음에는 미보유, 특수 사건 성공 시 Lv.1 획득 또는 Lv.2 강화, XP 없음**
- 이벤트별로 Lv.1 보너스 / Lv.2 전용 보너스 또는 선택지 해금 구분 (전역 공통 보너스 없음)
- 입사 시 상사 1 + 동료 2 랜덤 생성, 같은 run에서는 지속성 유지
- 이벤트 선택지: 2~4개
- 합격 확률 안전 범위: 5~95%
- **소비 자원은 0~100, 영구 능력치는 미보유/Lv.1/Lv.2 (XP 없음)**
- 급여, 자산 및 지출은 `KRW` 정수

### 13.2 반드시 확인할 밸런스 항목

- 특정 배경/전공/특성이 압도적으로 좋은가?
- 영구 능력은 처음에 없지만, 특정 출신 배경이 능력 획득 경로를 사실상 독점하지 않는가?
- 희귀 사건을 통한 능력 획득·강화가 특정 경로에 편중되거나 과도한 스노우볼을 만들지 않는가?
- 좋은/나쁜 NPC 출현률과 이벤트 불이익이 공정한가?
- 연말 평가 및 연봉 조정이 반드시 정확히 1회씩 실행되는가?
- 플래그의 범위·유효기간·회사 이동 후 생존 여부가 정확한가?
- 연속 고위험 사건·선택지 0개·이벤트 반복으로 인한 교착이 있는가?
- F등급 시작자가 의미 있는 확률로 B/A등급까지 올라갈 수 있는가?
- S등급 고연봉이 건강/행복 손실 없이 항상 최적이 되는가?
- 실업·해고·파산에서 회복할 수 있는 경로가 있는가?
- 극단적 운만으로 합격·승진·자산이 결정되지는 않는가?
- 유사 이벤트 반복 때문에 지루해지지는 않는가?
- 단일 회차가 지나치게 길거나 짧지는 않은가?

### 13.3 자동 시뮬레이션

랜덤 시드 1,000~10,000개를 사용하는 자동 플레이 봇(기본/안전/고위험 전략)을 추가하고 다음 분포를 출력한다.

- 은퇴 도달률, 파산률, 조기 종료율
- 최종 순자산 분위수, 최고 직책 분포
- 회사 등급별 입사/이직/승진 결과
- 반복 이벤트 상위 20개, 선택지 사용률
- 전략별 자산·행복·명성 트레이드오프
- 능력별 Lv.1 획득률, Lv.2 강화률, 획득/강화 사건 등장 빈도, 희귀 보상 편향
- NPC 성향별 이벤트 성공률/평균 승진/멘탈 손실 분포

수치의 절대 기준보다 **특정 전략이 무조건 이기는지**를 우선 분석한다.

## 14. 품질·보안·테스트

### 14.1 단위 테스트

- 동일 이름·성별·시드에서 동일 카드 3장, 모든 카드 이름·성별 동일
- 이름·성별 입력 오류 검증, 클라이언트가 후보 카드 데이터 변조 시 차단
- 동일 시드에서 동일 캐릭터 카드/이벤트/NPC/판정 재현
- 입사 시 NPC 3명 생성, 새로고침/재접속 후 변경 없음, 이직 시 새로운 팀 생성
- NPC 성향 및 관계값이 적격 이벤트/성공 보정에만 적용
- Lv.1 보너스 이벤트에서는 Lv.1부터 적용되고, Lv.2 전용 이벤트에서는 Lv.1에 보너스가 없음을 확인
- 일반 이벤트 성공에는 영구 능력 보상 없음; 특수 사건에 명시된 성공 결과에서만 획득/강화
- 성공 판정 후 특수 사건의 획득/강화, 해당 선택에 새로 획득한 능력 보너스가 소급 적용되지 않음
- 능력 획득·강화가 중복 요청에서 한 번만 발생
- 조건 불일치 이벤트가 선정되지 않음
- 단기 자원 0~100 상·하한 및 영구 능력 미보유/Lv.1/Lv.2 상태 유지
- 화폐 정수 처리/월간 정산/부채 계산
- 선택지 성공·실패 효과 정확히 적용
- 강제 후속 이벤트가 예약된 시점에 발생
- 이벤트 쿨다운/횟수 제한 준수
- 게임 종료 후 다음 턴 진행 불가

### 14.2 통합/E2E 테스트

- 새 게임 → 이름·성별 입력 → 동일 프로필 카드 3장 생성 → 카드 선택 → 입사 → NPC 생성 → 특수 사건 성공/영구 능력 획득·강화 → 저장 → 이어하기
- 지원 실패 → 재지원 → 취업 가능
- 승진/이직 성공 후 적절한 직무 이벤트 발생
- 관리자에서 초안 작성 → 검증 → 게시 → 새로운 세션에 노출
- 두 번 클릭/네트워크 재시도로 이벤트 결과가 중복 반영되지 않음
- 게임을 완료한 뒤 결과와 랭킹에 일관된 값 저장
- 360px 내외 모바일 너비에서 필수 UI가 잘리거나 겹치지 않음

### 14.3 운영 안정성 및 보안

- 서버에서 확률과 결과 확정, 세션 소유권 검증
- 관리자 권한 분리, 입력 검증, 감사 로그
- 서버 요청 제한(rate limiting), 과도한 요청 방지
- 데이터베이스 마이그레이션 및 백업·복구 절차
- 구조화 로그에 `runId`, `turn`, `eventId`, `engineVersion` 저장
- 중요한 상태 전이는 트랜잭션 + `stateRevision` 낙관적 동시성 검증. 발생/판정/정산별 난수 호출 순서 명시
- 게스트 토큰은 안전한 쿠키/세션으로 보관, 관리자 API는 별도 역할 검증; 문서/로그에 토큰·이름 등의 민감정보를 불필요하게 남기지 않는다
- 사용자 개인 정보 최소 수집, 비밀키는 환경변수 관리
- 게임의 실제 사회·경제·연봉 통계처럼 보일 수 있는 값은 **가상 밸런스 수치**임을 고지

## 17. Claude Code 작업 방식과 협업 규칙

### 17.1 작업 단위

기능별로 다음 순서를 지킨다.

1. **현황 점검:** 관련 코드·DB·테스트를 먼저 읽는다.
2. **작은 계획:** 변경할 파일과 범위, 필요한 데이터 마이그레이션을 명시한다.
3. **구현:** 가능한 최소 단위로 커밋 가능한 변경 수행.
4. **검증:** 타입 검사, 단위 테스트, 통합 테스트 또는 수동 재현 절차 실행.
5. **보고:** 변경 파일, 동작 확인 결과, 미완료 항목, 다음 작업 제시.

### 17.2 피해야 할 구현

- 모든 이벤트를 React 컴포넌트의 거대한 `switch`/`if` 문으로 처리
- 프론트엔드만으로 채용/승진/자산 판정을 확정
- `Math.random()`을 여러 위치에서 직접 호출하여 결과 재현 불가
- JSON 문자열로 저장된 조건을 `eval`로 실행
- 게임 밸런스 수치를 여러 파일에 복붙
- 관리자 페이지에서 발행 즉시 기존 진행 중 플레이의 이벤트 정의가 변경
- 서버 처리 없이 버튼을 두 번 누르면 돈/능력치가 두 번 증가
- 실제 테스트 없이 “완료” 보고

### 17.3 개발 시 결정이 필요한 질문(기본값 포함)

| 결정 | 임시 기본값 | 변경 가능 여부 |

| 시작 연령 | 24세 | 가능 |
| 플레이어 프로필 | 시작 시 이름·성별 입력, 카드 3장 모두 동일 | 필수 |
| NPC 수 | 입사 시 상사 1명·동료 2명 | 확장 가능 |

| 은퇴 연령 | 60세 | 가능 |
| 한 턴 | 1개월 | 초기 고정 권장 |

## 18. Claude Code 첫 프롬프트 (이전 버전 기록; 실제 착수는 §24 사용)

이 프롬프트는 이전 버전의 기록으로 남겨둔다. **실제 신규 개발 시작은 §24.2의 최신 프롬프트를 사용한다.**

```text
이 프로젝트는 '회사원 키우기'라는 모바일 우선 선택지형 로그라이크 웹게임이다.
첨부된 DEVELOPMENT_PLAN.md를 먼저 처음부터 끝까지 읽고 이 문서를 기준 명세로 사용해줘.

우선 저장소와 기존 코드/패키지/테스트를 확인해. 기존 구현이 있다면 절대 무단으로 덮어쓰거나 삭제하지 마.
그리고 다음 순서로 작업해줘.

1. 현재 상태 요약 및 핵심 설계 결정을 짧게 정리
2. Phase 0 및 Phase 1의 작업을 실행 가능한 작은 단위로 분해
3. Phase 0부터 구현: 웹/API/공통 타입, 게임 상태 머신 및 시드 기반 RNG 기반 구조
4. 최소 단위 테스트를 추가하고 실제 실행 결과를 보고
5. Phase 1의 첫 번째 플레이 흐름(이름·성별 입력 → 해당 프로필이 공통인 랜덤 캐릭터 카드 3장 생성 및 선택)을 구현
6. 긍정·부정 영구 특성은 둘 다 시작 시 빈 컬렉션. XP 없이 긍정은 특수 사건 성공으로 획득/강화, 부정은 특수 실패·위험 선택에서 부여/악화되며 특별 극복 사건에서 완화/제거. Lv.1 및 Lv.2 이벤트 효과를 각각 테스트
7. 회사 입사 시 시드 기반 상사 1명·동료 2명 랜덤 생성, 성향/관계 저장 및 NPC 이벤트 연동의 최소 구현

필수 원칙:
- TypeScript 타입 안정성
- 서버 확정 게임 상태와 확률 판정
- 게임 엔진/UI/콘텐츠 데이터의 분리
- 게임 이벤트의 선언형 JSON 스키마 및 검증
- 모바일 우선 UI
- 코드 변경 후 테스트 수행, 실패를 숨기지 않기

초기에는 창업, 투자, 결혼, AI 이벤트 생성, 결제, 앱스토어 배포 등을 구현하지 마.
§20~§24의 규칙/스키마/검증 기준을 본문 최신 기준으로 적용하고 과거 버전 부록의 옛 프롬프트는 무시해.
작업 후 변경 파일 목록, 테스트 명령과 실제 결과, 남은 이슈, 다음 우선순위를 보고해줘.
```

## 19. 성공 기준과 개발 방향 요약

이 게임의 경쟁력은 실제 회사 이름이나 복잡한 숫자가 아니라 다음 세 가지다.

1. **내가 선택한 행동이 몇 년 뒤 예상하지 못한 결과로 돌아오는 재미**
2. **같은 이름·성별이라도 랜덤 카드·회사 NPC·특수 사건으로 획득한 능력에 따라 전혀 다른 인생이 나오는 재플레이성**
3. **돈이 많거나 높은 직책에 올랐다고 반드시 최고의 인생은 아닌 엔딩 설계**

따라서 **이름·성별 입력 → 랜덤 카드 생성 → 취업/NPC 생성 → 월간 이벤트/특수 사건 능력 획득·강화 → 이직 → 은퇴 결과**의 수직 슬라이스를 가장 먼저 완성한다. 플레이가 재미있다는 검증 후 관리자 도구와 콘텐츠 생산성을 강화하고, 그다음 경제·가족·창업 시스템으로 확장한다.

> **최우선 목표:** 처음 실행한 사람이 하나의 인생을 끝까지 플레이하고, 결과가 달라질지 궁금해서 바로 새 게임을 누르게 만드는 것.

## 부록 A. v1.2 변경 기록 및 Claude Code 검증 우선순위

**변경 요약:** (1) 모든 신규 run의 `skills = {}`; (2) 이름·성별 지정 후 생성되는 3장의 카드 모두 영구 능력 미보유; (3) XP와 자동 레벨업 완전 폐지; (4) 특수 랜덤 이벤트 성공으로 Lv.1 획득 및 다른 명시적 특수 이벤트 성공으로 Lv.2 강화; (5) 이벤트마다 Lv.1과 Lv.2 성공률 보너스/선택지/실패 피해 감소 등을 독립 설정; (6) NPC 성격·관계와 특수 사건의 조건 연결.

**필수 자동 테스트:**

1. 새 게임·랜덤 카드 3장 모두 획득한 영구 능력 0개.
2. 일반 업무 이벤트 100회 성공해도 `grants/upgrades`가 없으면 변화 없음.
3. 특수 획득 사건 성공으로 빈 컬렉션에 정확히 Lv.1 생성, 실패 시 미생성.
4. Lv.1 강화 조건을 충족한 특수 사건 성공에서만 Lv.2, 실패 시 Lv.1 유지.
5. 이미 보유한 능력 재획득은 Lv.2로 자동 변경되지 않음.
6. Lv.1 유효 이벤트에서 Lv.1 보너스 적용, Lv.2 전용 이벤트에서 Lv.1에는 보너스 미적용.
7. Lv.2에서 이벤트별 정의된 최상위 보너스 하나만 적용(누적 중복 금지).
8. 서버 중복 요청·재시도에도 능력은 한 번만 획득/강화.
9. 저장·이어하기 후 `skills`와 `skillHistory` 일치.
10. NPC 조건·아이템 조건·기타 확률 보정과 영구 능력 이벤트별 보너스가 정상 합성되고 최종 확률 제한 준수.

**기존 v1.1 구현이 존재할 경우:** 실제 저장소와 DB를 확인하고 구형 `{level,xp}` 데이터를 새 `{skillId: level}` 구조로 옮기는 **명시적 마이그레이션 계획**을 먼저 작성한다. 기존 사용자의 영구 능력치 처리(초기화/변환/레거시 세이브 분리)는 사전 정책 결정 없이 임의 삭제하지 않는다. 신규 개발이면 v1.2 구조만 구현한다.

**이전 변경 프롬프트(이력 보존용, 사용 금지; §24 최신 프롬프트 사용):**

```text
DEVELOPMENT_PLAN.md v1.2를 기준으로 개발해줘.
이전 영구 능력치 설계(XP, 시작 레벨 부여, Lv.2부터 일괄 보너스)는 폐기한다.
모든 신규 run은 skills={}로 시작하며 캐릭터 카드 3장 모두 영구 능력 0개다.
특수 이벤트에 명시한 성공 결과로만 Lv.1 획득·Lv.2 강화할 수 있다.
이벤트마다 Lv.1/2에서 발동하는 확률 보정과 특수 선택지를 별도로 데이터 정의한다.
일반 이벤트 성공만으로는 스킬 변화가 없도록 서버에서 강제한다.
변경이 필요한 모델, 이벤트 엔진, 관리자 입력 폼, 세이브, 테스트부터 점검하고
작은 구현 단계와 검증 방법을 제시한 뒤 진행해줘.
```

## 20. 필수 보완 A — 정기 이벤트·실업 복구·고정 턴 규칙 (v1.4 확정)

### 20.1 턴 처리 단일 계약

- `turnIndex=0`은 시작 나이 24세의 **1월**로 정의한다. `yearIndex=floor(turnIndex/12)`, `monthOfYear=(turnIndex % 12)+1`, `age=24+yearIndex`. 나이 표기와 연도는 게임 내 가상 연도로 표시한다.
- 한 달은 `MONTH_START → SETTLEMENT → SCHEDULED_CHECK → EVENT_PENDING → EVENT_RESOLUTION → MONTH_SUMMARY` 순으로 **정확히 한 번** 처리한다. `MONTH_SUMMARY` 확인 후 다음 달로 넘어가 `turnIndex`를 +1 한다. **정기 평가와 급여 조정은 랜덤 선택 이벤트 제한에 포함하지 않는 자동 처리**다. 선택 미해결 중에는 월 진행 불가.
- **12월 평가**는 독립적인 `annual_review` **정기 시스템 판정**이다. 월간 선택 이벤트 1개와 별도 처리해 연말에 랜덤 이벤트 때문에 인사평가가 누락되지 않게 한다. 12월 평가에서는 성과, 재직 기간, 직책별 요구조건, 회사 상황, 상사 신뢰도를 참고해 승진 포인트/평가등급을 확정한다.
- **다음 해 1월 연봉 조정**은 지난 12월 평가를 참조한 `salary_adjustment` 정기 처리로 딱 한 번 실행하며 `annualReviewProcessedYear` / `salaryAdjustedYear` 체크포인트로 중복 실행을 막는다. 급여 조정은 **1월 급여 정산 전에 적용**하고, 최초 시작 1월에는 직전 평가가 없으므로 조정하지 않는다.
- 긴급 예정 이벤트가 12월에 있어도 연말 평가는 수행한다. 월간 사건 표시는 예정된 후속 이벤트가 우선하고, 강제 이벤트가 여러 개라면 `dueTurn`, `priority`, `scheduleId` 순으로 처리한다. **MVP는 한 달에 선택이 필요한 **랜덤/예약 사건**을 최대 1개만 표시**하고 나머지는 다음 달로 이월하되 `maxDelayMonths=3` 내 처리하도록 한다.
- 고용 상태 `EMPLOYED`, `UNEMPLOYED`, `ON_LEAVE`, `RETIRED`, `ENDED`. 월간 정산은 고용 상태마다 다르게 처리. 휴직의 급여는 MVP에서는 0으로 두고 복직 이벤트로 관리(가상 규칙).

### 20.2 실업·재취업·채무와 게임 오버 방지

- 채용 실패/권고사직 후 `UNEMPLOYED` 전환. 고용 관계는 종료하되 과거 NPC와 업적/플래그는 보존한다. **실업 중에도 월간 생활비·부채 이자 지출**과 사건이 진행된다.
- 기본 생활형 행동은 `구직(3개 지원 카드 갱신)`, `임시 일거리(소액 수입·체력 소모)`, `휴식(체력/정신 회복)` 중 고른다. Phase 1 최소 구현은 `구직 + 임시 일거리`; 휴식은 기본 이벤트로도 가능.
- 채용 카드 3개 중 하나 이상은 **충분히 지원 가능한 F~D등급 대안**으로 제공하며, 여러 번 불합격해도 세션이 불가능한 상태로 고정되지 않게 한다. 성공을 100% 보장할 필요는 없지만 `N회 연속 불합격(초기값 4)` 후 직업소개/단기 계약 이벤트를 강제로 제안한다.
- 돈이 부족하면 `cash`를 음수로 방치하지 않고 부족분만 `debt`에 전환, 현금은 최소 0을 유지한다. `cash`, `debt`, `totalEarned`는 원화 정수로 저장. 부채 이자율은 명시적 게임 설정(초기 월 0.5%)을 사용하고 **실제 금융 안내로 오해되지 않도록 가상 수치 표시**.
- 부채 초과는 즉시 종료가 아니라 경고·생활 수준 하향·채무 조정 이벤트의 계기가 된다. 가상 파산 조건은 **부채 1억 원 이상 + 6개월 연속 음의 현금흐름 + 채무 조정 실패** 등 복합 조건으로 잡되 초깃값은 설정화한다.
- 체력/정신력 0 도달 시 별도 `CRISIS_PENDING` 회복 선택지를 제공하고, 선택 불가능 상태에서는 자동 안전 구제(휴식/임시 휴직)를 적용한다. 조기 종료는 명시적인 특별 사건/조건에서만 처리한다.

### 20.3 정기 처리 수용 테스트

1. 12월에 강제 연쇄 이벤트가 발생해도 연말 평가는 1회 처리된다.
2. 같은 1월 정산 요청을 2번 보내도 인상/급여 지급이 중복되지 않는다.
3. 실업 6개월 동안 생활비/이자가 매월 계산되고, 임시 수입·재지원이 가능하다.
4. 채용 실패가 반복되어도 유효한 구직 선택지가 적어도 하나 존재한다.
5. `cash + debt` 계산이 아닌 **`cash - debt`**로 MVP 순자산을 계산하며, 금액은 언제나 정수다.

## 21. 필수 보완 B — 플래그 범위·NPC 역할·이벤트 안전장치

### 21.1 장기 기억/플래그 데이터 계약

`flags`는 단순 문자열 배열 대신 아래 레코드를 표준으로 사용한다. `scope`로 적용 경계를 명시하여 이직 후에도 남는 업계 소문과 회사 내부 갈등을 분리한다.

```json
{
  "key": "reported_manager_misconduct",
  "scope": "NPC",
  "ownerId": "npc_123",
  "value": true,
  "createdTurn": 18,
  "expiresTurn": null,
  "sourceEventId": "evt_report_manager"
}
```

- 범위는 `RUN`(이번 인생 전체), `COMPANY`(특정 회사), `NPC`(특정 인물), `TEMPORARY`(지정 만료 시점). `TEMPORARY`는 `expiresTurn` 필수, 나머지는 nullable. **만료 판단은 `currentTurn >= expiresTurn`이면 비활성**.
- 현재 회사에서 생긴 플래그는 `companyId`를 소유자로 지정한다. 이직해도 데이터는 보존하되 해당 회사/인물에 관한 사건에서만 유효하다. 재입사하면 해당 회사의 유효 플래그가 다시 적용된다.
- `RUN` 플래그는 이직 이후에도 적용된다. NPC 소속이 바뀌어도 NPC 범위 플래그는 `npcId`를 따라간다. 필요하면 명시적 해제 이벤트(`clearFlag`)를 제공한다.
- 반복 `setFlag`는 `(runId, key, scope, ownerId)` 기준 덮어쓰거나 명시적 `append` 규칙을 따르며, 기본은 중복 생성하지 않는다.
- 미정의 플래그·존재하지 않는 회사/NPC/후속 이벤트 ID는 콘텐츠 게시 전 검증한다. `scheduledEvents`에는 `dueTurn`, `priority`, `eventId`, `sourceOccurrenceId`, `status`를 저장한다.

### 21.2 NPC 승진·이직·교체 시 일관성

- 직속 상사의 직급은 **현재 플레이어보다 높아야 한다**. 상사보다 높은 직급으로 승진하면 기존 상사는 `FORMER_BOSS`로 관계 이력에 남기고, 더 높은 직급 NPC를 재배치/생성한다.
- 플레이어가 초기 MVP의 최고 직급인 `DEPARTMENT_HEAD(부장)`에 도달하면 NPC 직급에 **확장 전용 `EXECUTIVE`**를 허용한다. 이는 NPC 계층 구성을 위한 것으로, 플레이어 임원 플레이를 Phase 1에 구현한다는 뜻이 아니다.
- 상사 변경 시 기존 NPC를 삭제하지 않고 `teamAssignments`의 유효기간(`fromTurn`, `toTurn`)만 수정. 새로운 상사 1명 + 활성 동료 최대 2명을 보장한다. 새 상사 생성은 별도 시드 스트림 사용.
- 동일 회사 재입사 시 기존 NPC가 재직 중이면 재사용하되, 역할 충돌 시 재배치한다. 다른 회사 입사 시 새 팀 생성. 개인 관계/기억은 NPC ID를 따라 유지.
- 같은 달에 승진과 조직개편이 함께 일어나면 **승진 판정 → 직급 업데이트 → 조직도 정합성 복구** 순서로 원자적으로 처리한다.

### 21.3 랜덤 사건 안전장치

- 월 선택 이벤트 최소 1개(조건 0개면 범용 `quiet_month`), 선택지 최소 1개는 항상 **표시 및 선택 가능**해야 한다. 기본 구조는 필터링 후 추첨이 아니라 **선택지 유효성을 포함한 후보 검증 → 추첨**이다.
- 같은 이벤트는 `cooldownMonths` 및 `maxOccurrencesPerRun`으로 제한. 기본 일반 이벤트는 직전 3개월 내 중복 금지(별도 명시 시 예외). 여러 이벤트가 동일 주제를 차지하지 않도록 `exclusiveGroup` 활용.
- 고위험 사건(큰 체력·정신·재정 손실)을 연속 **2개월** 겪은 뒤에는 다음 달에 강제/예약 사건을 제외하고 회복 가능 사건을 우선한다. 예정된 고위험 후속 사건은 삭제하지 않고 안전한 선택지/피해 완충을 부여한다.
- `quiet_month`는 모든 상황에서 가능한 안전한 폴백이며, 직무별 직책·아이템 소유와 무관하다. 효과는 작은 자연 회복만 제공하고 무한 자금 증식이 없도록 한다.
- 부정 특성 획득/악화는 **명시된 특수 사건만** 처리하며, 일반 실패가 누적되었다는 이유로 자동 획득시키지 않는다.
- 모든 연쇄 이벤트는 유효한 `eventId`, 각 선택 결과의 후속 조건, 최대 예약 지연을 검증하고, 무한 예약 루프는 게시 시 거부한다.

## 22. 필수 보완 C — 정보 공개·특성·콘텐츠 규모

### 22.1 확률 공개 정책

- **채용 지원 카드:** 정확한 합격률(%) 공개. 등급/직무/연봉/위험도 함께 표시.
- **일반 사건 선택:** 정확한 성공률·RNG 시드·숨겨진 NPC 신뢰 수치는 비공개. 대신 `낮음/보통/높음`의 **위험 등급**, 보유 특성의 **적용 유무와 이름**, 선행 조건 및 비용을 표시한다.
- 위험도 표시는 서버가 현재 상태의 보정 후 확률에서 결정: 성공률 `>= 0.7 → 낮음`, `0.4~0.699 → 보통`, `<0.4 → 높음`. 모든 구간은 임시 정책이며 관리자가 버전별 조정할 수 있게 한다.
- 보유한 능력이 Lv.1이고 해당 이벤트가 Lv.2만 인정한다면 **보너스 적용 표시를 하지 않는다**. 잠겨 있는 특수 선택지는 요구되는 능력의 이름/레벨을 보여주되 숨겨진 이야기 자체는 스포일러하지 않는다.
- 확률을 보여주지 않더라도 선택 전 예상 체력·돈 지출처럼 **확정 비용**은 표시한다. 결과가 랜덤임을 명확히 고지한다.

### 22.2 선천적 특성과 사건 획득 특성의 경계

| 구분 | 저장 필드 | 초기 상태 | 성장 규칙 |
|---|---|---|---|
| 출신/성향/선천적 강점·약점 | `backgroundTraits[]` | 카드마다 다름 | **레벨 없음**; 직무·기본 보정으로만 작동 |
| 긍정 후천적 영구 능력 | `skills` | `{}` | 특수 사건 **성공** `0→1`, 별도 강화 성공 `1→2` |
| 부정 후천적 영구 특성 | `negativeTraits` | `{}` | 명시된 실패/위험 선택 `0→1`, 특수 사건 `1→2`, 극복 사건 `2→1→0` |
| 체력/정신력/집중력 등 | `resources` | 카드에 따라 다름 | 매달/사건별 증감; 영구 특성 아님 |

- 콘텐츠 제목에서 선천적 성향 `압박에 약함`과 후천적 영구 특성 `유리멘탈`을 구분해 혼동을 피한다. **선천적 특성은 특수 사건 보상으로 Lv.2가 되지 않는다.**
- 사건 획득 **긍정 6종·부정 6종의 정의/설명/효과는 등록**하지만 Phase 1에서 실제 획득·강화/극복 이벤트를 만들 우선 목록은 긍정 `socialSkill(처세술)`, `crisis(위기대응력)`, `observation(관찰력)`, 부정 `burnout(번아웃)`, `officeStigma(사내 낙인)` 총 5종이다.
- 그 외 7종은 마스터 데이터만 등록하고 개발 단계에서 실제 이벤트가 연결되기 전에는 **비활성/발견 불가** 상태로 둔다. 업적/도감 수집률에도 포함하지 않는다. 사용자에게 빈 특성 슬롯만 여러 개 보여주지 않는다.
- 계정별 **능력치 도감**은 Phase 4 이후 확장. Phase 1은 `이번 인생에서 발견한 특성` 목록과 획득 순간의 연출만 구현한다.

## 23. 구현 계약 — 데이터 스키마·상태·API·테스트 확정

### 23.1 상태의 단일 출처

- 서버의 `GameRunState`를 게임 규칙의 **유일한 진실 원천(source of truth)** 으로 삼는다. 플레이어 화면용 view model은 이 상태에서 **공개 가능한 정보만** 투영한다.
- `GameRunState` 최소 구성: `runId`, `userId/guestOwnerId`, `seed`, `rngState`, `engineVersion`, `contentVersion`, `stateRevision`, `turnIndex`, `phase`, `profile`, `selectedCharacter`, `characterCards`, `jobOffers`, `employment`, `resources`, `cash`, `debt`, `skills`, `negativeTraits`, `backgroundTraits`, `flags`, `scheduledEvents`, `eventOccurrences`, `activeEvent`, `npcs`, `npcAssignments`, `eventHistory`, `annualReviewProcessedYear`, `salaryAdjustedYear`, `statistics`, `finishedAt`.
- **하나의 정본 상태 + 불변 로그**를 우선하고, 성능상 필요한 테이블 정규화/스냅샷은 그 다음이다. `stateRevision` 증가는 모든 성공적 상태 변경과 원자적으로 수행된다.
- `GameRunState` 필드/선택지/효과는 Zod 스키마(혹은 동등한 타입 안전 검증기)로 검증하며, 실제 DB 마이그레이션과 API DTO가 동일한 버전 계약을 따른다.
- 콘텐츠 버전은 **새 플레이 생성 시 고정**하여 세션 진행 중 관리자 수정이 결과를 바꾸지 않도록 한다. 과거 이벤트 ID는 보관해도 재생/저장에 필요한 버전은 삭제하지 않는다.

### 23.2 이벤트 효과의 표준 형태

과거 문서의 `grants`, `skillGrant`, `upgrades`, `negativeTraitGrant` 같은 예시는 **동일 목적의 표현 예제**였고, v1.4부터는 `effects[]` 배열을 **서버와 관리자 공통 최종 스키마**로 확정한다. 기존 이벤트 시드 데이터는 이 형태로 정규화한다.

```json
{
  "id": "evt_social_breakthrough",
  "version": 1,
  "status": "published",
  "special": true,
  "category": "social",
  "rarity": "rare",
  "weight": 10,
  "cooldownMonths": 6,
  "maxOccurrencesPerRun": 1,
  "conditions": {"employment": "EMPLOYED", "skillAbsent": ["socialSkill"]},
  "choices": [
    {
      "id": "mediate",
      "label": "갈등을 중재한다",
      "visibleIf": {},
      "enabledIf": {},
      "outcome": {
        "baseChance": 0.4,
        "modifiers": [{"source": "SKILL", "id": "socialSkill", "levels": {"1": 0.10, "2": 0.12}}]
      },
      "onSuccess": {"effects": [
        {"type": "RESOURCE_DELTA", "key": "reputation", "amount": 5},
        {"type": "SKILL_SET_LEVEL", "id": "socialSkill", "from": 0, "to": 1}
      ]},
      "onFailure": {"effects": [{"type": "RESOURCE_DELTA", "key": "mental", "amount": -5}]}
    }
  ]
}
```

- **기본 효과 타입**: `RESOURCE_DELTA`, `CASH_DELTA`, `DEBT_DELTA`, `SKILL_SET_LEVEL`, `NEGATIVE_TRAIT_SET_LEVEL`, `NPC_RELATION_DELTA`, `FLAG_SET`, `FLAG_CLEAR`, `SCHEDULE_EVENT`, `EMPLOYMENT_CHANGE`. 미지의 타입은 게시/실행 거부.
- `SKILL_SET_LEVEL`: `0→1` 또는 `1→2`만 가능. **특수 이벤트 + onSuccess**에서만 허용. `NEGATIVE_TRAIT_SET_LEVEL`: `0→1`, `1→2`, `2→1`, `1→0`만 가능하며 명시된 특수 사건 분기에서만 허용한다.
- 동일 능력/특성의 레벨을 1개 선택 결과 내에서 두 번 변경하지 않으며, 실행 시 현재 레벨이 `from`과 다르면 **전체 트랜잭션 실패** 또는 사전 스키마 검증에 의해 해당 이벤트 비적격 처리한다. 성공률은 변화 전 레벨만으로 계산.
- 확률 보정은 `baseChance + Σ(skill 최고 충족레벨 1개/능력별) + Σ(negative trait) + Σ(NPC) + Σ(item) + Σ(situational)`을 `0.05~0.95`로 clamp. `levels`는 **누적이 아닌 치환형**(Lv.2의 0.12는 Lv.1 0.10에 더하지 않는다). `%p`와 배수 `percent`를 혼용하지 않는다.
- 명시적 `guaranteedEffects`/`onSuccess.effects`/`onFailure.effects`는 **각각 적용 시점**이 다르므로 구현에서 구분한다. 같은 필드에 효과 객체와 숫자 변화량을 혼용하지 않는다.
- 이벤트 데이터에 보이는 모든 `id`(회사, NPC 템플릿, 특성, 후속 이벤트)는 게시 시 사전 존재 검증하고 무한 후속 이벤트 경로는 제한한다.

### 23.3 API 상태 전이 표 (필수)

| 현재 상태 | 허용 명령 | 다음 상태 | 중복·오류 처리 |
|---|---|---|---|
| `PROFILE_INPUT` | `createCards` | `CHARACTER_SELECTION` | 생성 결과 서버 고정 |
| `CHARACTER_SELECTION` | `chooseCharacter(cardId)` | `GOAL_SELECTION` | 서버 발급 ID만 허용 (S5: 인생 목표 후보 3장 고정) |
| `GOAL_SELECTION` | `chooseGoal(goalId)` | `JOB_OFFERS` | 제시된 목표만 허용 (S5) |
| `JOB_OFFERS` | `apply(offerId)` | `MONTH_START` 또는 `JOB_OFFERS` | 합격 시 NPC 3명, 실패 시 구직 월 진행/재지원 |
| `MONTH_START` | `startMonth` | `EVENT_PENDING` 또는 `MONTH_SUMMARY` | 정산 및 정기 처리 1회 |
| `EVENT_PENDING` | `choose(eventId,choiceId)` | `EVENT_PENDING`(다음 사건) 또는 `MONTH_SUMMARY` | 한 달 2사건(업무→일상, S4); idempotencyKey + revision 확인 |
| `MONTH_SUMMARY` | `nextMonth` | `MONTH_START` 또는 `GAME_OVER` | 턴 +1; 위기 상태 확인 |
| `GAME_OVER` | `getResult` | `GAME_OVER` | 쓰기 거부 |

- 최초 `POST /api/runs`는 프로필 검증과 카드 생성을 **한 트랜잭션**으로 수행하여 `CHARACTER_SELECTION` 상태를 반환한다. 위 `PROFILE_INPUT → createCards`는 개념적 내부 전이이며, 클라이언트가 별도로 호출하는 API가 아니다.
- `JOB_OFFERS`는 **취업 대기 단계**이며, 실제 월 진행이 필요한 실업 중에는 월 상태 머신으로 들어가고 구직 행동이 이벤트/명령으로 연결된다. 하나의 API에서 같은 월을 두 번 진행하지 못한다.
- API 쓰기 요청은 `idempotencyKey`(최소 선택/지원/정산)와 `expectedRevision`을 포함. 같은 키·같은 본문은 이전 결과 반환; 같은 키·다른 본문은 409. `expectedRevision` 불일치도 409.
- API 오류는 `code`, `message`, `details`, `requestId`의 표준 형태이며, 잘못된 상태 409, 요청 데이터 오류 400, 비인증 401, 권한 없음 403 등으로 구분한다.

### 24.1 최초 1회 준비

1. 파일을 프로젝트의 `docs/DEVELOPMENT_PLAN.md`로 복사한다. 실제 개발 명령은 프로젝트 루트에서 실행.

## 26. v1.5 개정 — 실직 게임오버와 엔딩 (2026-11-17 사용자 승인)

> **우선순위: §26은 아래 표의 기존 조항보다 우선한다.** 결정 경위는 `docs/SPEC_AMENDMENT_v1.5.md`.

### 26.1 핵심 규칙

- **50세 미만 비자발적 실직 = 즉시 게임오버(실패 엔딩).** 50세 이상이면 같은 원인이라도 **조기 은퇴(정상 엔딩)**로 끝나며 원인은 보존한다. 기준 나이는 `rules.gameOver.failureBeforeAge`(초기값 50).
- **0이 되면 즉시 실직하는 소비 능력치:** 체력 → 과로 실직, 정신력 → 번아웃 실직, 집중력 → 대형 사고 실직, 평판 → 사내 퇴출. 완충 선택지는 없다.
- **부채 한계선:** 월말 부채가 `연봉 × rules.gameOver.debtLimitSalaryMultiple`(초기값 3) 이상이면 즉시 빚더미 퇴장. 가상 설정임을 표시한다.
- **이벤트 실직:** 해고·구조조정·권고사직·폐업. 반드시 사전 징후(경고 플래그)를 거친 뒤에만 발생한다.
- **자발적 퇴사 선택지는 50세 전까지 제공하지 않는다.** 이직은 새 회사가 확정된 경우에만 허용(Phase 2).
- **숨김 NPC 관계 0은 엔딩이 아니다.** 해고 징후 플래그의 계기로만 쓴다.
- **60세 도달 = 정년 은퇴.**

### 26.2 판정 시점과 우선순위

- 그 달의 이벤트 선택이 끝나 `MONTH_SUMMARY`로 들어갈 때 판정해 `pendingEnding`에 기록한다. 요약 화면에 원인을 보여 주고, `nextMonth` 명령에서 `GAME_OVER`로 전이한다(턴 증가 없음).
- 원인이 겹치면 다음 순서로 **한 가지만** 적용한다: 체력 0 → 정신력 0 → 집중력 0 → 평판 0 → 부채 한계 → 이벤트 실직. 정년은 `nextMonth`에서 나이가 은퇴 연령에 도달할 때 판정한다.
- 엔딩 제목·문구는 콘텐츠 데이터(`endings.json`)에서 직무·특성·관계·자산 조건별 변형 중 첫 일치를 사용하고, 판정 시점 문구를 상태에 고정 저장한다. 톤은 블랙코미디, 건강 표현은 의학적 진단처럼 쓰지 않는다.

### 26.3 사전 경고

- 체력·정신력·집중력·평판이 `rules.gameOver.warningThreshold`(초기값 20) 이하이면 공개 뷰 `warnings[]`에 표시한다. 부채가 한계선의 70% 이상이어도 경고한다.
- 위 경고 상태에서는 `recovery` 태그 이벤트의 가중치를 `rules.gameOver.recoveryWeightBonus`만큼 올린다.
- 확정 비용(`guaranteedEffects` 및 `ALWAYS` 조건부 효과)만으로 0 또는 부채 한계에 닿는 선택지에는 "⚠ 선택 시 (엔딩 제목)" 경고를 붙인다. 확률이 걸린 결과는 위험 등급만 표시(§22.1 유지).

### 26.4 첫 구직 보장

- 첫 구직(입사 이력이 없는 상태)의 세 번째 카드는 항상 **F등급·합격 확정(100%)**이다.
- 다른 카드에 불합격하면 화면에 보였던 그 F 카드의 회사·직무·연봉으로 **자동 입사**한다. 불합격 비용(정신력 -5)은 유지한다. 따라서 첫 구직은 반복되지 않는다.

### 26.5 데이터 계약

- `EMPLOYMENT_CHANGE` 효과는 `status: UNEMPLOYED` + `reason ∈ {LAYOFF, RESTRUCTURING, FORCED_RESIGNATION, COMPANY_CLOSURE}`만 허용한다(자발적 사유 없음).
- 실직 효과를 가진 이벤트는 (1) `conditions.flagsAll`에 경고 플래그를 요구해야 하고, (2) 그 플래그를 세우는 다른 이벤트가 있어야 하며, (3) 조건 없이 고를 수 있고 성공·실패 어느 결과로도 실직하지 않는 선택지가 최소 1개 있어야 한다. 위반 시 콘텐츠 검증 실패.
- 상태에 `pendingEnding`, `ending { type, cause, category: FAILURE|NORMAL, age, turnIndex, sourceEventId, title, text }`, `finishedAt`을 둔다. `GAME_OVER` 이후 쓰기는 409.

### 26.7 수용 테스트

1. 49세 체력 0 → 과로 실직(FAILURE), `nextMonth`에서 `GAME_OVER`. 50세면 조기 은퇴(NORMAL), 원인 보존.
2. 정신력·집중력·평판 0, 부채 한계 각각 해당 엔딩. 동시 발생 시 우선순위 1개만.
3. 실직 이벤트는 경고 플래그 없이는 후보가 되지 않고, 규칙 위반 콘텐츠는 검증에서 거부.
4. 20 이하 경고 표시, `recovery` 가중치 가산, 확정 비용 치명 선택지 경고.
5. `GAME_OVER` 이후 쓰기 409, 저장 후 재조회 시 `ending` 동일.
6. 60세 도달 시 정년 은퇴.
7. 첫 구직은 어떤 카드를 골라도 입사로 끝난다.
8. 자동 플레이에서 진행 불능 상태 0건.
